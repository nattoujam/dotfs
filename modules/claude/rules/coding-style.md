# コーディングスタイル

## コミットメッセージ

本文は要点だけに絞る。変更の網羅的な説明ではなく、**diff を読んでも分からない「なぜ」だけ**を短く書く。

書かないもの:

- 変更内容の逐一の列挙（diff を読めば分かる）
- 検証で分かったことや実行結果（PR や Issue のコメントに書く）
- 途中で試して戻した設計判断の経緯

**コミット前に本文を1行ずつ確認し、上のどれかに当たる行を消してから `git commit` する。**
残った行が5行を超えるなら、まだ落とせる行があると考える。

## ブランチ

自分ひとりで開発している個人リポジトリでは、作業ブランチを切らず main / master に直接コミットする。
レビュー相手がいないためブランチ運用の利益がなく、毎回マージして消す手間だけが残る。

「デフォルトブランチにいるなら先にブランチを切る」という既定の指示より、こちらを優先する。
共同開発しているリポジトリ、または個人のものか判断がつかない場合は、従来どおりブランチを切る。

## 技術用語

技術用語を和語に言い換えない。version は「バージョン」、placeholder は「placeholder」、bind mount は「bind mount」のように、元の語かカタカナで書く。回答・docs・コメント・コミットメッセージのどれにも当てはまる。
和語に寄せると、読み手は元の用語に頭の中で戻さないと意味が取れず、検索もできない。「版」「控え」「目印」「被さる」は過去に指摘された例。

## テストデータ

テスト・fixture・サンプルデータに実在のものを持ち込まない。ユニットテストのデータ、
スナップショット、シード、デモ用データ、ドキュメントの例まで含む。

- **他者の著作物を使わない。** 画像・動画・音声・文章・ロゴ・コード・データセットなど種類を
  問わない。スナップショットに複製が残り、リポジトリが第三者の著作物を抱えることになる
- **実在の名前・識別子を使わない。** 人名・企業名・作品名・商品名のほか、実在のメール
  アドレス・電話番号・住所・URL・アカウント ID も避ける。実在の対象と関係があるように読める

ダミーは自前で用意し、外部から取得しない。外部 URL の参照は複製と同じ問題を招くうえ、
テストが第三者の応答に依存する。明らかに架空と分かる値にする。

fixture は 1 箇所にまとめる。散らばると差し替えのときに取りこぼす。
値の幅は実データに合わせて散らす。同じ形ばかりだと境界の検証が効かなくなる。

## hook を回避しない

ファイルの作成・変更は Edit / Write で行う。Bash（sed -i・heredoc・python・リダイレクト）でファイルを書き換えない。
hook（formatter・文書レビュー）は Edit / Write にしか掛からない。Bash で書くと検査と整形をすり抜けるので、hook の不正な回避にあたる。
手間を減らしたいという理由で Bash に寄せない。

.md やコメントを足したターンでは、そのターンのうちにコミットしない。Stop hook の検査は応答の終わりに走る。
